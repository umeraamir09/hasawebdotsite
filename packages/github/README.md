# GitHub storage contracts

Phase 11D provides calendar projection and credential handling in `src/`. Phase 40 adds `src/public.ts`, the production public fetch. Phase 41 adds `src/oauth.ts` (activity consent) and `src/authorized.ts` (the owner-token calendar). Phase 42 adds `src/refresh.ts`, the refresh policy and message. Provider experiments in `spike/` retain their historical evidence.

`public.ts` ports the Phase 11C classifier for the separate zero-scope platform credential. `resolvePublicIdentity` turns a typed username into the canonical login and stable GraphQL account ID. `fetchPublicBaseline` returns `available` (zero contributions included), `unavailable`/`restricted`, `retry` (credential, rate, server, network), `invalid` (scope, identity, payload) or `not_found`. `publicRefreshResult` maps it to the persistence form, where a missing or renamed account clears the baseline and a transient failure keeps the last good calendar. `lookupLoginById` suggests a username from a GitHub sign-in's numeric ID and selects nothing. `parseContributionCalendar` is the shared allowlist parser that Phase 41's authorized fetch reuses. GitHub aligns calendars to whole weeks, so the parser accepts up to six days of padding either side of the requested window and drops those days; dates further out, duplicates and an empty result are `invalid`. Requests use `redirect: "manual"`, because Workers reject `"error"`. A redirect response counts as a provider failure. A platform failure is never an owner reconnect.

`oauth.ts` builds the activity app's authorize URL (`read:user`, S256 `code_challenge`, the selected `login`, `allow_signup=false`), creates 256-bit URL-safe states and verifiers, hashes states for storage and exchanges a code with its verifier. `exchangeActivityCode` returns any delivered token, even with the wrong scope, so the caller can revoke it; otherwise it reports that no token reached the adapter. `hasActivityScope` accepts `read:user`, alone or with the sign-in app's `user:email`, and nothing broader.

`authorized.ts` reads GraphQL `viewer` and the selected user's calendar with an owner token, an activity token or the owner's GitHub sign-in token. `fetchViewer` names a token's account and scopes; the owner's own graph starts there. `fetchAuthorizedActivity` names the token's account whenever GitHub answered, so consent can reject another account without enabling it. A 401 is `credential` (reconnect), never retry. `authorizedRefreshResult` maps a wrong scope or account to the reconnect errors that withdraw the grant, and reuses `parseContributionCalendar`, so only dates and counts are kept.

`RefreshResult` distinguishes an independently safe public baseline from a complete authorized calendar. The latter includes public and private contributions. Never add calendars or subtract independently fetched counts. The Phase 11C public-baseline classifier remains the required provider policy. Platform failures must not become owner reconnect errors. Public identity/scope/payload failures discard the baseline; transient errors retain the last successful calendar and its fetch date.

`projectPublishedActivity(published, state)` accepts the immutable graph configuration from the active publication, including stable account ID, username, and `includePrivate`. A missing publication returns no graph. Mismatched identity/generation returns unavailable. Authorized output requires both the publication's private choice and currently valid authorization. Returned fields are allowlisted. Owner previews need a separate authenticated adapter. Never pass draft choices into the public endpoint.

`encryptActivityToken` uses AES-GCM with a random IV and a portfolio/app/account/consent-operation binding. Only internal jobs may decrypt active credentials. Cleanup credentials live in separate storage and are unavailable to refresh acquisition. Keys and app secrets come from server configuration. Key provisioning/rotation remains later integration work.

Rejected post-exchange tokens use a separate authenticated binding purpose and the verified account identity. After decryption authenticates that purpose, cleanup uses [GitHub's single-token endpoint](https://docs.github.com/en/rest/apps/oauth-applications?apiVersion=2026-03-10#delete-an-app-token). This revokes the rejected credential without withdrawing another account's active grant. Existing grant bindings and grant-wide withdrawal keep their original semantics.

Grant deletion uses [GitHub's grant-wide endpoint](https://docs.github.com/en/rest/apps/oauth-applications?apiVersion=2026-03-10#delete-an-app-authorization), which removes all OAuth tokens for the app/user pair. Only HTTP 204 confirms deletion. Requests use `redirect: "manual"` because Workers reject `"error"`; a redirect is a retry. Other completed HTTP responses retain encrypted credentials for retry after one minute. An interrupted request is uncertain and keeps consent blocked. A clock-based lock expiry cannot stop a provider request that is already running.

One exception releases a credential without a 204 (Phase 41). When GitHub already refused the token with 401 during a refresh (`providerRejected`), the token can never delete anything again. A 404/422 from the delete is then followed by [GitHub's token check](https://docs.github.com/en/rest/apps/oauth-applications?apiVersion=2026-03-10#check-a-token), which documents 404 for an invalid token. Both observations together return `gone`, which releases cleanup like `deleted`. A 404 alone, or any check result other than 404, stays a retry.

`refresh.ts` (Phase 42) holds the owner-approved intervals: `REFRESH_TTL_MS` (six hours, counted from the last successful fetch), `REFRESH_REQUEST_WINDOW_MS` (15 minutes: deduplication, lost-message recovery and transient-failure retry), `PRIVATE_SWEEP_INTERVAL_MS` (one day) and `PRIVATE_SWEEP_BATCH` (25 per cron tick). `calendarDue` treats a missing, unreadable or future-dated calendar as due. `parseRefreshMessage` accepts only `{ kind: "github-refresh", portfolioId, requestedAt }`; the message carries no identity, token or count.
