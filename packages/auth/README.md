# Shared authentication

Web provider routes and the named jobs owner API use this package's Better Auth configuration. It retains the verified-only GitHub/Google linking rules, host-only cookies, exact apex origin and persisted session/deletion checks established in Phase 11.

`productAuth` caches library configuration in a WeakMap keyed by the binding environment. `currentOwner` resolves identity for each request with the cookie cache disabled, then constructs repositories which recheck persisted session and deletion state. Do not retain identities or repositories globally.

Configure the same `APP_ORIGIN`, signing secret and provider credentials in web and jobs. The local example files document these values. Normal social sign-in permits only `/auth/entry` paired with its provider-specific sign-in error destination. Draft recovery permits only `/auth/recovery` paired with `/auth/recovery/error`. Reject arbitrary URLs, query variants and mixed pairs. Connecting another provider (`link-social`) permits only `/editor?account=connected` paired with `/editor?account=not-connected`, for a signed-in owner who has not connected that provider; ID tokens, scopes and extra data are rejected. `accountLinking.allowDifferentEmails` is on because Better Auth reads it only for this explicit, OAuth-proven link; sign-in still auto-links only on a matching verified email. The account create hook keeps one account per provider per owner. Listing and disconnecting providers are jobs owner routes (`apps/jobs/src/provider-routes.ts`). The browser persists an identifier-only tab continuation and checks uncached owner identity before opening recovery. Secrets are never forwarded as request headers. The named `OwnerApi` binding receives the original request cookie, and jobs independently authenticates it. Jobs' default HTTP entry does not expose owner routes.


Owner summary reads keep their default shape. Explicit `include=profile-suggestions` adds the stored sign-in name and supported-photo availability. Explicit `include=email-suggestion` adds only the private account email suggestion. Both require a matching `X-Expected-Owner-Id` and persisted owner authorization. No photo URL, token or automatic draft mutation is introduced. `providerPhotoUrl` owns the exact HTTPS image-host policy shared by suggestions and private web retrieval.
