# Shared draft client

Create one controller per authenticated owner/portfolio and mounted flow. Obtain both IDs from the owner API, never from a URL or local recovery. Leave `id` unset in product adapters; it is a deterministic test hook, and each mounted flow needs a unique recovery record. Call `initialize()`, render `DraftStatus`, subscribe with Zustand and dispose on unmount/account exit. Initialization can reject with a typed blocked state while still exposing recovery metadata.

`edit(path, value)` accepts field paths containing stable selectors such as `["components", { id: "projects-1" }, "data", "entries", { id: "project-1" }, "title"]`. Valid values update the working draft immediately; invalid values remain in `inputs` and return false. Render that field's raw input in preference to its working value. `setInput` and `clearInput` support controls with their own unfinished representation. `update(validDraft)` applies coherent structural edits, including reorder/removal. Field adapters must clear compatible sample markers when owners edit sample content, using the schema's existing helpers.

The controller debounces valid edits for two seconds, coalesces changes and serializes commands. `changeProgress` is setup-only. A single bounded operation uses patch; grouped/large changes stage and commit once. New edits during a request remain separate from the immutable batch and retain their own two-second debounce, including while waiting for a tab lock. Explicit flush drains all valid edits. Ordinary acknowledgements update the confirmed snapshot without another complete read.

`flushValid()` returns `{ revision, hasLocalOnlyInput }` after confirming all current valid edits and waiting for queued local persistence. This includes unfinished-input-only navigation with no network write. It rejects while blocked or saving fails. It does not validate ready uploads, required setup, publication or provider access. Handoff may retain invalid optional input; Publish must resolve all current unsaved input and required uploads. Neither caller may equate a staged sequence with a saved revision.

`retry()` reconciles uncertain replies before continuing. Staged sequence advancement requires identical-command replay to verify the server receipt hash. `resumeAttempt()` explicitly transfers a recoverable attempt after session changes. An uncertain command whose receipt belongs to another session remains blocked: return to that session or explicitly discard staging, since transfer clears its receipt hash. `discardAttempt()` explicitly discards staging while retaining local input and canonical content. Its durable intent pins the displayed attempt ID and records confirmation before cleanup; Retry finishes that discard after a lost abort/cleanup reply, including a durable revision/setup block. Restoring a discard journal retains its working values and original comparison base before finishing only the pinned cleanup. A changed base still requires selected review afterward. Session transfer checkpoints the expected cursor and accepts exactly one increment, including an idempotent replay after a lost reply. An older receipt cannot replace an already known newer canonical snapshot. Expired/revoked attempts require reconciliation before bounded cleanup. Known revision conflicts and setup closure remain blocked, including after reload or a later account change. Retry cannot clear these blocks. The Phase 15 recovery coordinator supplies explicit review/resolution and fresh controller scopes. The controller never merges newer drafts or reopens setup on Retry. The coordinator applies only explicitly reviewed selections.

Recovery records contain a version, random record ID, authenticated owner/portfolio IDs, context, base snapshot, working draft, private progress, stable raw-field values and immutable command/receipt, session-transfer and explicit-discard journals. They contain no credentials or source files. Records remain private to the browser origin and are listed only for the active owner/portfolio. Restore/discard is explicit. A changed base blocks replay. A conflict notification received during an acknowledgement remains blocked and durable even if the acknowledged batch itself finished. Recovery records retain the blocking reason so another reload cannot turn an input copied for review into a clean-base edit. Unfinished input also blocks cross-tab base refresh. Applicable setup records remain available to later editor field adapters after handoff; do not replay setup progress or automatically convert setup batches to content writes.

Pending server metadata has no staged content. Without the original local journal, an unfinished content attempt cannot safely continue or commit. Return to its original browser or explicitly discard staging. A lost `begin` receipt has no verifiable attempt ID: even sequence zero may belong to another device with different captured setup progress. Explicitly discard that staging and flush the preserved local batch again. Web Locks cannot establish identity across devices. Validation also requires its matching journal: metadata can contain another browser’s private destination correction and cannot authorize committing it. An untouched sequence-zero validation clone can recover a locally journaled lost validation-begin because it captures only the immutable canonical base. `validateLegacy()` continues bounded traversal and permits correction only at its reported destination. `setValidationInput(value)` persists correction text promptly, separately from sent commands, bound to the issue path and base revision. `clearValidationInput(key)` removes explicitly reviewed local text. Successful validation clears only current raw values equal to the exact acknowledged canonical revision; newer or differently based input remains local and makes `flushValid().hasLocalOnlyInput` true. Discarding staging retains correction text for explicit resubmission at the same base; field adapters must review values from other revisions. Structural/reference failures and unsupported versions require original-draft download/maintenance.

IndexedDB failure leaves memory editing and acknowledged cloud saving available with a visible recovery warning. It cannot promise interruption recovery. Disposal/checkpointing does not rely on unload network requests. Web Locks serialize origin-local commands; BroadcastChannel carries revision and attempt-ID notifications only, without draft content. Without Web Locks, server CAS/sequence checks remain authoritative. Unknown attempts are never automatically adopted.

Injected storage adapters must honor `remove(id, expectedSnapshot)` as an atomic compare-and-delete. Restoration and older acknowledgements must preserve a source record that its original tab has updated. If replacement persistence fails, retain the durable source instead of deleting its only recoverable copy. Browser recovery uses idb-keyval transactions for this check.

React field adapters must reset local control state when `controller.scopeKey` changes. The shared status controls do so, and a controller that observes `owner_changed` remains stopped. Create a new controller only after obtaining the current authenticated owner/portfolio IDs. Dispose standalone controllers before leaving a flow. For a coordinated flow call `recovery.dispose()`, which closes its current and temporary replacement controllers and prevents later writer creation or command dispatch after storage waits. Disposal preserves local checkpoints; it does not flush new network writes.

Every draft/progress request carries `X-Expected-Owner-Id`. The server compares this precondition to the real authenticated identity and returns `owner_changed` on mismatch. It never uses the header as authorization. A returned portfolio-ID mismatch also blocks the client.

The fixture in `apps/web/integration/autosave-fixture.tsx` and `scripts/autosave-browser.mjs` is separately bundled for `pnpm test:autosave`. No production route imports it. It uses the production web forwarding adapter and jobs router with isolated D1 and signed fixture sessions. The Phase 17 editor adapter is exercised separately by `pnpm test:editor`; full editor/onboarding activation remains later work.

## Selected review and same-tab recovery

Mount `DraftRecovery` with `createRecoveryCoordinator({ ownerId, portfolioId, context, controller })`. Subscribe to its store's current `controller`; replacements change `scopeKey`, so field adapters must reset and disable fields while `state.suspended` is true. `start(recordId?, choice)` quiesces the controller, settles its in-flight acknowledgement, checkpoints its latest state and separately fetches canonical content. Unresolved staging/validation still needs its original journal or explicit discard before review. Ordinary Retry never resolves revision/setup blocks.

`compareRecovery` compares original base, local working values and current canonical values. Scalar changes preserve unrelated newer fields. Stable IDs match entries across reorders. Add/remove/order, rich text, discriminator/link/date/category/case-study changes are explicit structural selections. Changed entries removed in canonical content remain nonselectable review values. Raw `inputs` and `validationInputs` stay separate; correction text retains its numeric issue path and original base revision.

`select` persists decisions before updating the UI. `apply` rechecks revision and milestone, clears selections on change and requires review again. Load newer version requires confirmation and keeps the original in a review-only copy. Apply selected changes creates and persists a fresh base/working scope, retains unselected values for review and uses existing serialized patch/staging saves. Remaining active raw input shows Unsaved input. Setup closure forces a fresh content context, preserving canonical progress and milestone. It never converts a setup attempt.

Version-1 records remain readable. Optional `review` holds versioned review/prepared/resolved decisions, selected IDs, canonical comparison and replacement ID. `reviewOnly` copies are listed but do not block initialization. Replacement records and decision checkpoints exist before source compare-and-delete. A concurrent source update survives. Starting a review from an archived record never retires the active scope's own recoverable checkpoint; it stays listed as a separate preserved recovery, and only a clean active record is removed. Reopen unfinished review after reload; explicitly dismiss retained copies. Storage failure retains durable originals and prevents leaving for sign-in. Starting review keeps the active controller usable until the review copy and continuation are durable; disposal finishes before conditional source retirement.

`leaveForRecovery(controller, provider)` persists a record and an identifier-only version-1 sessionStorage continuation, then uses same-tab recovery sign-in. `/auth/recovery` and `/auth/recovery/error` first call uncached owner status, verify owner/portfolio, and only then open that account's recovery range. Explicit Continue preserved edits quiesces the controller before source lookup and keeps fields suspended through restoration. It releases the pause before receipt verification/saving, or on failure; changed bases require review. Wrong-account, cancelled and failed returns retain the original continuation/records. Callback replay with a retired record falls back safely. Matching callbacks always offer ordinary account entry, including clean checkpoints and expiry before the initial draft read. No draft content or credentials enter URLs. Normal sign-in remains `/editor`; the recovery callback does not provision or activate guide/editor routing.

The isolated autosave fixture enables Phase 15 controls with `?recovery`; its default mode preserves Phase 14 regression coverage. The auth fixture serves a separately bundled recovery helper for real auth-handler/provider-fixture journeys. Neither helper is imported by production routes. Browser evidence covers Chromium only; Phase 53 retains the complete release matrix. Deployment CPU feasibility from Phase 14 remains unresolved.

Continuation retirement follows replacement persistence. Restoration updates a matching tab continuation to the durable replacement record before deleting the original source. Callback reload can therefore offer remaining unfinished input without repeating a confirmed write. A changed-base staging discard checkpoints its original `reviewBase` and durable block before cleanup clears the journal, preserving the three-way comparison through a crash.

Selected structural objects carry forward unrelated newer fields while applying their coupled values together. Quiescence gates subsequent legacy-validation and content commands after the in-flight acknowledgement. Clean replacement checkpoints do not block initialization and successful no-write replacement removes its empty active record. If authentication expires during review, sign in from the persisted review checkpoint; its selected decisions survive. Final application remaps a matching continuation to the replacement record/context, including fresh content recovery after permanent setup handoff.

Review may retire an already committed terminal receipt after separately reading canonical content and durably preserving local values. The review checkpoint links the fresh content controller's explicit cleanup journal, so a lost cleanup reply or reload continues the same pinned intent. This does not resume an uncertain command, adopt unknown unfinished staging or acknowledge the local target. A discard checkpoint with `id: null` means no attempt was observed and must reject an attempt that appears later. Field adapters must disable editing both while the controller is suspended and while coordinator review is active.

Prepared replacement recovery mounts a fresh record scope rather than reusing the old writer ID. Suspend that controller before exposing it to fields and keep it suspended through restoration, then release before receipt verification or saving. Before resuming an unexecuted replacement, recheck canonical revision/milestone; if changed, preserve its target in a review-only copy, refresh the original comparison and clear selections. Existing command journals still reconcile receipts instead of silently rebasing. Attempt conflicts also expose deliberate review choices; open unknown staging remains blocked for its journal or explicit discard.

## Editor integration

`apps/web/components/editor-session.tsx` supplies the content/customization panels, stable component selection and field adapters. Its authenticated owner/portfolio scope opens the existing content draft without provisioning or applying initialization. It follows coordinator replacements and resets selection/control state by `scopeKey`. Raw values override valid working values in fields; accepted edits clear only matching legacy sample markers. Fields are disabled during suspension, review and coordinator operations. Prepared review quiesces the active controller before its first source-storage lookup, including failed restoration.

`EditorPreview` sends only a cancellable display projection to the shared iframe bridge. It uses actual 1120- or 390-pixel child viewports independent of the available editor width. Save status and acknowledged preview status remain separate. Image preparation checks owned-ready-purpose access through private asset reads and reuses successful resolutions by purpose/asset ID within the mounted owner/portfolio scope. Text edits reuse these resolutions; failed reads remain retryable, and replacement IDs require new reads. Removed references leave the cache. The image URLs still require authorization on every HTTP request. The toolbar's `Open full-page preview (saved draft)` link opens `/preview`; [`openFullPreview`](../editor/full-preview.ts) reads the saved draft from the server (never the working copy), resolves images with `resolvePreviewImages({caseStudies})` and mounts the page with `mountPreviewPage`, and [`previewRequest`](../editor/preview-route.ts) gates the routes in the Worker (see [authentication](../../../../docs/authentication.md#full-page-draft-preview-authorization)). The dormant `serveEditorPreview` and `openEditorPreview` adapters for the iframe child perform owner checks before serving/mounting the child. Browser restoration rechecks the original identity; owner change removes the previous display.

`controller.identity` exposes the frozen owner/portfolio IDs for request preconditions. Shared `ProfileControls`, `ProfileImages` and `SocialLinksControl` use this identity and the existing controller for draft edits. Profile name/bio/location fields share the existing raw-input adapter. Explicit provider name acceptance clears its sample marker; suggestions alone never edit the draft. Provider-photo sources, crop sources and upload progress stay local to a mounted control. Mounted image controls report transient pending flags to the controller while opening, cropping, uploading or retaining a failed upload for retry. Cancel, successful acceptance or unmount clears the flag; blobs are never persisted in draft recovery. `ProfileControls` can hide optional editor location for the future onboarding adapter. Its missing-field feedback excludes sample values and unaccepted avatars; authoritative owned-ready validation remains the setup/publication services' responsibility. Only a ready finished crop becomes a draft reference. The shared link list preserves IDs and both placement flags. Invalid link type/destination input remains in the controller's recoverable raw fields. Looking up account email never edits the draft; public acceptance is a separate action. A qualifying-link helper supplies the profile-link subset for later authoritative setup validation.

`ComponentControls` supplies the registry-driven picker and section list. It uses empty registry defaults, enforces singleton limits before insertion and reports draft-size failures without changing the working draft. Profile is outside the optional order. Text titles identify multiple sections. `OrderedItems` is reusable by guided adapters and entry editors, with dedicated pointer/touch handles, keyboard sorting and Move up/down buttons. `moveEditorItem` resolves stable IDs against the current controller state for sections, project/work/skill entries and skill categories. Existing shared social-link controls retain their own ordering.

`ProjectControls` edits the selected projects component through the same controller and stable entry paths. `addProject` creates an empty owner entry without samples and rejects draft-size failures before insertion. Title/summary can save incomplete and show publication feedback. Invalid URLs and over-budget field values remain local recovery input; repairing/removing the entry clears its own raw fields. Technologies use one line per saved string. Entry ordering reuses `OrderedItems`, and removal requires explicit confirmation. Project images reuse `ImageUpload` with purpose `project`, without a forced crop; only ready uploads replace references. Upload failures retain the previous image, pending operations block publication, and image removal clears its description input. The same controls can be mounted by future onboarding adapters without a separate project store. See [Phase 28 results](../../../../specs/2026-10-28-project-cards/results.md).

`TextControls` uses Tiptap for the selected text section's title and structured body. Its extension set supports paragraphs, headings 2–6, bullet/numbered lists and safe links only. Link and ordered-list attributes match the existing strict schema. The controller validates full-draft changes and retains rejected body edits as owner-scoped raw input; publication blocks unfinished input. Pasted HTML becomes allowed structured nodes, and rendering remains controlled React markup. Link insertion requires selecting text and applying a validated HTTP(S) or mailto destination. Each section is keyed by controller scope and stable component ID, and follows controller replacement, review and suspension. Shared section ordering/removal applies unchanged. See [Phase 29 results](../../../../specs/2026-10-28-safe-rich-text/results.md). Since Phase 30 the editor is the shared `RichTextEditor`; text sections omit the image extension.

Each project entry adds `CaseStudyControls` (Phase 30). Add case study creates a `{slug, body}` case study, Remove case study requires confirmation and clears its raw inputs. The body reuses `RichTextEditor` with the case-study schema and a block-only `image` node whose attributes are only `assetId` and `alt`. That node has no HTML parse rule, so pasted or dropped images and `<img src>` never create nodes; images are inserted only after a ready `case_study` upload, after the top-level block holding the cursor. Each image reuses `ImageUpload` for replacement, removal, description and pending-publication state. `ProjectControls` loads frozen slugs from `POST /api/owner/publication/case-studies` on mount and after each successful Publish, then restores frozen slugs and regenerates unfrozen ones (`lib/editor/case-studies.ts`). Title edits regenerate an unfrozen slug and never change a frozen one. Add case study waits for that address check. The save planner sends slug changes as field patches unless a new slug takes another entry's previous slug, which keeps large case-study bodies out of title-edit saves. See [Phase 30 results](../../../../specs/2026-11-06-project-case-studies/results.md).

Every section removal, including the publication-correction shortcut, opens the shared modal confirmation. Cancel and Escape preserve the draft and restore focus; confirmation clears only that component, its sample marker and its raw field inputs. Shared links and private asset records are not deleted. Removing a GitHub component first withdraws private access through `POST /api/owner/github/withdraw` (Phase 41), even when the draft shows public activity only, because a grant can exist without being shown. The helper refuses GitHub removal without that confirmation, and a failed withdrawal keeps the section. Component-specific publication requirements remain in the schema validator. These controls are active in the handoff fixture; production editor/guide activation remains Phase 42E. See [Phase 27 results](../../../../specs/2026-10-28-component-controls/results.md).

The [Phase 17 browser suite](../../../../scripts/editor-browser.mjs) uses real signed sessions and the production owner API through an explicit handoff fixture. Phase 42E mounts the editor at `/editor` and registers the iframe document at `/editor/preview` behind the owner-entry gate (`lib/owner-entry-gate.ts`); with the gate closed, product `/editor` stays the welcome shell. The deployment feasibility checks remain release gates.

## Address confirmation

`confirmAddress(name)` flushes earlier valid content through the same controller, then captures the current revision and setup progress. It checkpoints an immutable Address command in the existing batch journal before sending. Address batches use the same serialized origin lock and recovery storage as ordinary saves. There is no separate save queue. A same-name legacy candidate still sends a confirmation and creates a hold.

A lost response retries the exact journaled command against its durable server receipt. A replayed receipt requires a current canonical read before acknowledgement. A newer mismatching revision blocks recovery and retains the journal and raw input for review. The historical receipt proves only that the original command committed. Draft string equality never proves reservation success. Changed command IDs/payloads and revision, account, or setup conflicts keep recoverable intent. Definitively rejected reserved/unavailable names retain raw input and the previous confirmed draft/hold; choosing another name permits a new confirmation. Receipts survive ordinary staging cleanup and remain for the portfolio lifetime.

`addressState()` reads the authoritative registry. `addressAvailability(name)` is advisory and never reserves. The reusable `AddressControl` stores raw typing through `setInput`, validates the shared format locally, and confirms only on Save address or form submission. It shows held/claimed status from registry reads or successful receipts. Ordinary Saved status does not establish a reservation. The control is mounted in the isolated editor adapter; production guide/editor activation remains separate. The field state lives in `useAddressReservation`, shared with the guide's Address step, whose Continue checks availability, calls `reserve()` and proceeds only when the registry confirms this owner's hold on the exact name.

## Setup guide

`SetupGuide` (Phase 42A) creates one setup-context controller and recovery coordinator per owner/portfolio and follows coordinator replacements by `scopeKey`, like the editor session. It renders `DraftRecovery` only when there is something to act on (failed/blocked saves, recoveries, review, journals); the header carries the Saving/Saved/Unsaved input/Couldn't save label. Navigation saves progress with `changeProgress` and `flushValid()` after the step's own content is confirmed. The shown step is never taken from the URL or from progress alone: [`resumeStep`](../guide/steps.ts) clamps saved progress to the first required step that [`checkSetup`](../guide/setup-check.ts) reports incomplete for the confirmed revision. Profile and Links (Phase 42B) host `ProfileControls` (`showLocation={false}`) and `SocialLinksControl`; Continue is blocked while an image is pending or raw input is unsaved, then runs `flushValid()` and a fresh setup check and advances only when the screen's fields (`stepFields`) are no longer reported. Skills and Projects (Phase 42C) are optional adapters over the editor entry mutations (`addSkill`, `addProject`, `moveEditorItem`, removals; categories and case studies stay editor-only). The component is created with its first entry; `settleOptional` drops entries nothing was typed into and an empty section on Continue or Skip, so an untouched step leaves no component, and a project with content but no title/summary blocks Continue yet survives Skip. Skip remaining steps targets `remainingTarget` (`review`). The optional GitHub screen (Phase 42D, `components/guide-github-step.tsx`, `lib/guide/github.ts`) renders the editor's `GitHubSetupPanel` with `returnTo="setup"` only after Add graph; `acceptGraph` creates the graph component when the setup route first accepts a username. Continue reads `GET /api/owner/github` and needs the account the draft names, a successful public fetch and, when the draft includes private activity, an authorized and fetched private calendar (`graphGap`); otherwise Finish later keeps the unfinished graph with its publication blocker. Before leaving for GitHub, the screen saves progress `github`, so consent and session recovery resume there. Skip never disconnects; Remove graph withdraws private access before removing the component. Sections the guide creates are inserted in Skills, Projects, GitHub order (`addGuideComponent`, `lib/guide/order.ts`), so revisiting an earlier screen cannot reorder them. Review (Phase 42E, `components/guide-review-step.tsx`) shows the confirmed saved draft through `EditorPreview` (no selection) and the `/editor/preview` document, lists `readPublicationIssues` for that revision without gating, notes local-only input, and runs `recovery.handoff()` from Open editor: `editor` replaces the tab with `/editor`, `required` returns the shell to the reported step, and a failure keeps the draft and offers Retry. A setup controller whose draft already has the milestone shows only Open editor. `OwnerEntry` (`components/owner-entry.tsx`) mounts the guide or the editor from `POST /api/owner/entry`; the gated `/auth/entry` and `/editor` pages render it, and the browser harness serves it at both paths. The direct `/guide` fixture remains for the 42A–42D groups.

## Required setup handoff

`handoffSetup(controller)` flushes valid edits, quiesces and persists the current setup controller, then submits its confirmed portfolio/revision to the authoritative handoff endpoint. Required raw input and valid changes after the flush prevent submission. Optional raw input remains browser-only recovery and the result reports `hasLocalOnlyInput`. No prepared setup batch or progress becomes a content batch.

Use `SetupHandoff` beside `DraftRecovery`. It calls `recovery.handoff()` through the coordinator's existing operation lock, preventing review/controller replacement during handoff. Failure releases the pause; revision/setup closure persists a block for shared selected review. A handoff `save_rejected` response maps to `attempt_conflict`, exposing recovery controls when another device starts staging after the last pending check. Recovery separately reads pending metadata and requires the original journal or explicit discard for unfinished staging. Authentication errors use the fixed recovery callback pair. Success leaves the old controller paused until unmount. A fresh content coordinator offers explicit selection of applicable preserved content. The isolated autosave browser fixture exercises this control; the complete guide remains Phase 42E.

## Publication checklist

`checkPublication` rejects pending image operations before and after flushing valid changes, so readiness never cancels a replacement by suspending its control. Once image work finishes or is explicitly cancelled, it quiesces the controller, rejects all local-only/unfinished input and active recovery, and checks every bounded asset page for one confirmed portfolio/revision. It retains issue failures across pages, rejects identity/revision changes and releases the pause on success or failure. This is an advisory saved-draft checklist, not a publication operation. The reusable editor fixture exposes it; explicit optional-section removal clears only that section's unfinished fields and preserves unrelated input. `/editor` activation remains Phase 42E.

Checklist issues open the required profile/image/link/address control or a focused correction panel. Catalog corrections offer the approved choices. Existing optional sections expose their current field controls or removal while later phases supply their complete setup tools. Component and nested entry correction targets retain stable IDs after opening, including unfinished input during reordering. Any subsequent draft change or pending image operation invalidates the displayed result. The integrated candidate and commit services recheck mutable facts. Phase 26 supplies the operation adapter below; paid-provider measurements remain release work.


`preparePublication(controller, submit, send)` reuses the same flush, image/input/recovery checks and paged readiness operation. It calls its admission adapter while the controller is still paused, with the exact confirmed owner/portfolio/revision. Checklist issues return `blocked`; an admitted candidate returns `preparing` after validating the response identity/revision. It never reports the candidate as live. The lower-level helper never reports a candidate as live. `publishSavedDraft` supplies the Phase 26 HTTP adapter and keeps editing paused through readiness, admission, polling, commit and withdrawal. It rejects pending uploads and local-only input before admission. A local identifier/revision hint and server operation discovery recover uncertain requests after reload. Retry preserves the original expected publication state and cannot restore an older pointer. Success requires a persisted commit and completed withdrawal. A cleanup failure reports the already-live version and offers Retry. The reusable checklist exposes Publish, stage messages, corrections and exact-URL Open/Copy in the editor handoff fixture. `/editor` activation remains Phase 42E.
