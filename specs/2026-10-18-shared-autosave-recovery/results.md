# Phase 14 implementation and verification

Implemented October 18, 2026 on `feat/shared-autosave-recovery`. The owner explicitly approved completion and requested a pull request on October 18, 2026. Phase 14 is checked in the roadmap; verification, costs, cleanup and activation prerequisites are recorded below.

## Implemented behavior

The shared client uses a controller-scoped Zustand store, explicit fetch, stable-ID field selectors and schema-aware bounded planning. Valid edits debounce for two seconds, including newer input arriving during a request or tab-lock wait. Automatic saves freeze one due batch; explicit flush drains queued valid work and waits for queued local persistence before controlled navigation. One bounded command uses patch, progress-only updates use progress, and grouped/large edits use staging plus one canonical commit. Saved requires a confirmed canonical revision and no unfinished local input.

IndexedDB recovery is versioned and keyed/range-read by owner, portfolio and random browser record ID. It retains canonical/working snapshots, raw unfinished JSON values, private progress and command/receipt checkpoints. It stores no source files or authentication credentials. Atomic compare-and-delete preserves source records updated by another tab. Failed replacement persistence retains the durable source. Storage failure preserves memory state and shows a recovery warning. Restore, session transfer and discard are explicit; changed-base recovery and unknown unfinished staging block rather than replaying over newer content. Reinitialization/restore cannot replace dirty working values. Disposal starts no new network commands, including after waiting for a tab lock or local checkpoint; in-flight receipts remain recordable. Shared controls reset confirmation/correction state when their controller scope changes. Applicable setup recovery remains available after handoff without converting setup attempts or replaying frozen progress.

Web Locks serialize same-origin command execution. BroadcastChannel carries only revision/attempt metadata. Server CAS and sequence checks remain authoritative across devices. Lost patch replies require canonical reconciliation; staged replies require identical-command receipt verification. Sequence advancement alone never acknowledges a command, and partial commits cannot confirm an entire captured batch. A lost begin reply cannot prove its attempt ID or captured setup progress, so explicit discard/rebuild preserves input safely. Session transfer is blocked until uncertain command receipts are verified. Committed receipts are checkpointed before cleanup. Validation uses bounded server-owned traversal and only explicit rejected-destination correction, with durable recovery of raw correction input and lost validation replies. Unfinished validation needs a matching journal because metadata cannot prove the identity of a private correction. Transfer checkpoints enforce one cursor increment; explicit discard checkpoints survive lost abort/cleanup replies and pin the intended attempt. Newer local input survives older acknowledgements, and older receipts cannot replace known newer canonical snapshots. An older acknowledgement cannot clear a newer conflict notification or its durable review record. A confirmed save followed by failed cleanup is reported as confirmed, and Retry does not repeat its commit.

Every draft/progress request now requires `X-Expected-Owner-Id`, compared against the authenticated identity. Missing headers return 400 `invalid_input`; mismatches return 409 `owner_changed`. This precondition never selects an owner or weakens persisted session/ownership/deletion checks. The client also checks the returned portfolio ID. Known revision conflicts and setup closure remain blocked across reloads; Retry does not resolve them or silently replace the working base underneath unfinished input. Owner change permanently stops that controller, including local restore/discard actions, until the controlled flow mounts a newly authenticated scope. Payload schemas, limits and migrations are unchanged. The CPU follow-up preserves streaming while increasing its bounded chunks from 16,384 to 65,536 Unicode code points. Draft/progress actions use a direct persisted access precheck instead of constructing unused general owner repositories; uncached identity lookup, session refresh and per-operation access predicates remain.

Shared React status/recovery controls reuse the Figma `12:48` reference's DM Sans, warm surfaces, text/control colors, spacing and ghost-button language. Figma design context and screenshot were read without changes to the file. The separately bundled integration fixture is excluded from production routes. `/editor` remains the welcome shell. Full conflict/reauthentication interaction remains Phase 15; editor/onboarding activation remains later work.

## Costs and remaining boundaries

See [measured requests and capacity calculations](quotas.md). Ordinary edits use one patch with no full follow-up read. The exact-size example uses 272 save/cleanup requests, 6,081 D1 reads and 1,036 writes. Ordinary representative patches cost 101 reads; maximum streamed reads now cost 76. Dense 3,000-component patches still scan roughly 12,000 rows; repeated maximum-field replacements and dense editing can exceed Free even with small payloads.

No production deployment, uploads, publication, editor/onboarding routes, connected-service integrations or full Phase 15 experience were added. Provider measurements used only isolated fixture resources, now removed with deletion/absence receipts. The retained configuration still needs KHI/intended-deployment CPU verification before dependent owner-flow activation; a passing LHE sample does not resolve the initial KHI failure or guarantee all warm/cold requests. Complete release browser/journey coverage remains Phase 53. Publication dispatch/cache-withdrawal feasibility and dormant-owner garbage collection remain their existing prerequisites.
