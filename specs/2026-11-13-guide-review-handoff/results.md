## Decisions

- **Activation gate.** `lib/owner-entry-gate.ts` opens only for `OWNER_ENTRY_ACTIVATION=active` on the web Worker. `/auth/entry` and `/editor` became per-request (`force-dynamic`) Next pages that read it through `getCloudflareContext` and render `OwnerEntry` when open or the unchanged `EditorEntry` welcome shell when closed (or when the environment can't be read). `editorPreviewRequest` registers `/editor/preview` in `worker.ts` only while the gate is open. Committed Wrangler configs leave the variable unset. The editor browser harness sets it in its generated web config to exercise the activated code; the auth browser suite runs the committed config and proves the closed side.
- **`OwnerEntry` is the single resolver.** It calls `POST /api/owner/entry` and follows only the persisted answer: setup → `SetupGuide` at `/auth/entry` (and `/editor` sends the owner there), entered → `EditorSession` at `/editor` (and `/auth/entry` forwards, keeping `?github=consent`, which closes the 42D gap). Navigation uses `location.replace`, so each side starts with fresh controllers. The editor header gains Sign out when a sign-out handler is supplied (always in production; fixtures omit it).
- **Review shows the saved draft.** It renders `confirmed.draft`, not the working copy, through `EditorPreview` with no selection and the production `/editor/preview` document, so the display projection, iframe bridge, owner-checked image reads and the Phase 40/41 graph preview adapter are the editor's. The "Open full-page preview (saved draft)" link reaches the Phase 39 pages. Layout and copy follow read-only Figma frames `326:558` (desktop Review), `330:487` (unfinished optional content) and `330:511` (editor entry could not finish); the Figma file was not changed.
- **Statuses are read, never enforced.** `readPublicationIssues` is the paged `/api/owner/publication/check` loop extracted from `withPublication`; Review calls it for the confirmed revision without flushing, pausing or preparing anything, and labels issues with the editor checklist's wording (`lib/draft/publication-labels.ts`). The server guard's `rejectSave` on that path is a classification read. A failed read offers Retry and still allows Open editor. Unsaved local input is named as browser-only and offered in the editor.
- **Handoff outcomes.** Open editor calls `recovery.handoff()` unchanged. `editor` replaces the tab with `/editor`. `required` writes the reported fields into the shell's clamp, so the guide returns to the first incomplete step with a notice and no milestone. Any thrown failure (lost request, conflict, expiry) shows "Your draft is safe" and Retry opening editor. A setup controller whose confirmed draft already has the milestone (another tab, or a reload after handoff) renders only "Your portfolio is in the editor" and Open editor, with no Back, Continue or skips.
- **Preserved setup input after handoff.** The fresh content controller lists the setup record as recoverable and, under the existing Phase 14/15 contract, blocks editing with `recovery_required` until the owner continues, reviews or discards it. Selected review shows the raw input separately ("Unfinished input, kept separately"), opens a fresh content scope and applies only selected changes; progress stays frozen. No setup attempt is converted and no progress is replayed. This blocking is existing behavior, not new policy; 42F may want to judge its usability.
- **Section order (ON-12).** `addGuideComponent` (`lib/guide/order.ts`) inserts a section the guide creates before any later guide section, so Skills, Projects and GitHub keep screen order even when an earlier screen is revisited after a later section exists (the 42D record's open gap). Editor insertion is unchanged.
- **Shared preview fixes.** `EditorPreview` accepts an optional selection and region label. Its scrollable stage is now a labelled, focusable region with a focus ring, fixing an axe `scrollable-region-focusable` violation found on Review; the editor gets the same fix.
- **Contact and grants.** The renderer's contact adapter stays "Contact form unavailable"; the guide never creates a contact component, and the display projection carries no recipient. The graph preview route returns calendars only, never grant or token data. Contact delivery (43–45) is the reason the gate stays closed; nothing here guesses its behavior.

## Results

Tested revision: working changes on `d4519d4` (branch `feat/42e-guide-review-handoff`, uncommitted at verification time). Profile: `full`, because the change touches the web Worker routing, the shared publication read, the shared preview component and every editor browser group (all `/editor` groups now run through the production `OwnerEntry` resolver and `/editor/preview`).

Implementation review (November 14, 2026), focused on the changed boundaries:

- **Gate.** Only the exact string `active` opens it; an unreadable environment keeps the welcome shell. With the gate closed, `/editor/preview` is not intercepted and returns the application's 404 (auth browser suite, committed config). Both pages are `force-dynamic`, `noindex` and no-store.
- **`/editor/preview`.** Same-origin GET only, owner check through `/api/owner` with the caller's cookie, data-free shell, `private, no-store`, `noindex`, `Vary: Cookie`, `frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN`. Review fix: a refused owner response body is now cancelled before returning, as the full-page preview route already does.
- **Review statuses.** `readPublicationIssues` is the unchanged paged loop moved out of `withPublication`. The server path is read-only: `guard` and `rejectSave` only `SELECT` and throw. A prepared setup attempt or a stale revision yields Retry check, never a save or a pause. Review fix: a `revision_conflict` while local input blocks the confirmed revision from advancing previously left the panel on "Checking" with no Retry; it now shows Retry check, and a newer saved revision still replaces it with a fresh read.
- **Handoff.** Review calls the unchanged Phase 22A `recovery.handoff()`. Only `editor` navigates; `required` clamps the shell to the reported step without a milestone; every thrown failure keeps the guide and offers Retry. `unauthorized`/`owner_changed` still surface through the existing `DraftRecovery` panel. A milestone already on the confirmed draft, or `setup_closed`, renders only Open editor.
- **Entry resolver.** `OwnerEntry` follows only the persisted `/api/owner/entry` answer and navigates with `location.replace`; 401 goes to sign-in. The contract always carries a portfolio.

Test fixes found during verification (test-only, no product change):

- `scripts/guide-github-browser.mjs` (42D): "Use public activity only" was followed by Continue before the asynchronous public-only request and draft write settled. The test now waits for the switch to uncheck. In the product a fast second click shows the "isn't authorized and fetched yet" message once and succeeds on retry; no data is affected. Left for 42F to judge.
- `scripts/github-graph-browser.mjs` (Phase 41, two places): the test waited for the removal button to stop matching a role query, then read `github_connection`. Instrumented runs showed the role query stops matching about 12–14 ms after the click while the dialog is still open with its disabled "Removing..." button and the withdrawal request is in flight. It failed in all three unmodified runs through the activated `/editor`. With the old editor fixture the role query stopped matching just as early, but the database read queued behind the withdrawal, so the check passed only by timing. Sampling the row showed `private_enabled` 0, `status` `disconnected` and a new generation as soon as the withdrawal returned, and the section was removed only after that. This is not a privacy regression. Both waits now wait for `dialog.component-removal` to unmount, which happens only after the withdrawal and the removal.
