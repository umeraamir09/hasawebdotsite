# Phase 41: Private activity, consent recovery and withdrawal

## Scope and acceptance

Requirements: [product section 9](../../docs/product.md#9-github-activity-graph), [acceptance criteria 9](../../docs/acceptance-criteria.md#9-github-activity-graph) (items 5–7, 9 and 11), [ON-09 to ON-11](../../docs/acceptance-criteria.md#initial-setup-checks) for the shared editor path, [architecture 8.5](../../docs/architecture.md#85-github-activity-product-9), the [Phase 11D storage and coordination contract](../2026-10-17-github-refresh-contracts/results.md) and the [Phase 41 roadmap entry](../../docs/roadmap.md#phase-41-add-private-activity-consent-recovery-and-withdrawal).

Change: an owner with a selected graph can turn on private activity, authorize the matching GitHub account through the separate activity OAuth app (`read:user`, one-use expiring owner/session-bound state, S256 PKCE), and see anonymized private counts in the private preview and, after Publish, on the live graph. Failed, cancelled or wrong-account consent keeps the public graph and offers Retry, public-only, or later repair. Removing private access or the graph withdraws private data immediately, without Publish, and revokes the grant at GitHub through durable retryable cleanup.

Acceptance checks (from the roadmap entry):

- Public/private preview and published output obey consent and Publish boundaries.
- Failure or a mismatched account never silently changes the selected user.
- Incomplete setup is repairable in the editor.
- Withdrawal removes private data without Publish despite racing jobs or failed remote revocation.
- A delayed old cleanup cannot revoke newly authorized access.
- Pending private cleanup cannot block public-only setup or editor entry.

Prerequisites (owner-approved and on `main` at `16677d6`): 06, 11D, 15, 40 (approved November 8, 2026), and the 26 withdrawal/cache boundary (approved October 28, 2026). Branch `feat/41-private-activity`, worktree `.claude/worktrees/phase-41-private-activity`. No delegated workers.

This phase does not touch `publication-cache.ts` or `packages/email`.

Write boundaries: `packages/github` (OAuth, authorized fetch, cleanup transport), `packages/db` (migration 0015, consent service, cleanup proof), `apps/jobs` (routes, cleanup sweep), `apps/web` (GitHub panel, removal withdrawal, private preview), the GitHub fixture and browser/integration harnesses, and current guidance.

## Decisions

- **Consent attempts are rows, not cookies.** Migration `0015_github_private_consent.sql` adds `github_consent`. A row stores the SHA-256 of a 256-bit state (never the state), the starting user and session, the reserved app/account/operation/generation from `beginConsent`, the PKCE verifier (kept only while `issued` or `exchanging`, enforced by a check constraint) and the fixed `editor` return. The callback consumes it with one compare-and-set on state, expiry, user, session and portfolio. Replays, other owners, other sessions and forged states change nothing and exchange nothing.
- **When a reservation may be released.** The 11D contract forbids releasing a reservation while an exchange may still complete. Releases happen only when (a) an `issued` attempt is voided by compare-and-set (restart, Public only, withdrawal, account change, or an expired callback), which the callback's own compare-and-set can then never consume; (b) the callback's own exchange settled without a token reaching the adapter (provider error or network failure): the fetch has finished, so no token can still arrive here; or (c) a crashed callback left the attempt `exchanging` for more than 15 minutes, past GitHub's ten-minute code lifetime and the ten-second exchange timeout. A delivered token is never dropped: it is enabled, or queued for token-only revocation. Case (b) is a judgment call for the boundary review: GitHub could have minted a token that never reached anyone. Such a token is held by nobody, and a later grant-wide revocation removes it.
- **Identity through GraphQL `viewer`.** The callback checks the token with the same contribution query the refresh uses, so the stable ID comes from the same API (GraphQL node ID) that public setup stored. REST `/user` could return a different ID format. The same response supplies the first authorized calendar. `finishConsent` stores the token only for the selected ID and username with exactly `read:user`. A token for another account or scope, or one whose account GitHub did not name, is queued for token-only revocation (`discardIssuedToken` was added for the unverified case).
- **Fixed return, outcome from status.** Every callback, including a signed-out one, answers `303 /editor?github=consent` with `Referrer-Policy: no-referrer`. The URL carries no outcome; the editor reopens the graph section and reads the persisted attempt outcome from `GET /api/owner/github`. Only the `editor` return exists; Phase 42D adds `setup`.
- **Dead-token proof for revoked access.** After GitHub refuses a token with 401 (the owner removed the app on GitHub), grant-wide deletion with that token can never succeed, so the 11D rule (only 204 releases) would block reconnect for that account forever. `github_grant.provider_rejected` records that the refresh saw a 401. Only for such grants, a 404/422 delete followed by GitHub's token check returning 404 ("Invalid tokens will return 404") releases cleanup as `gone`. Without the earlier 401, a 404 is still never proof. This narrows, rather than removes, the 11D rule and needs boundary review.
- **Withdrawal keeps the public selection.** Remove private access and graph removal call `disconnect`, so the generation advances, the token and authorized calendar are cleared and the grant is queued, while the public selection and calendar stay for the still-published public graph. Withdrawal and Public only need no platform token or activity app, so a misconfigured provider never blocks removal. Graph removal always withdraws first, even for a public-only draft, because a grant can exist without being shown; a failed withdrawal keeps the section.
- **Draft choice versus grant.** The draft's `includePrivate` is the owner's choice and goes live with Publish (frozen in the sealed index as in Phase 40). Authorization and withdrawal act at once. Changing the username turns `includePrivate` off in the draft and the server transition withdraws the grant. Owner preview follows the draft choice (`/preview?private=1`) and shows private counts only while the grant is currently valid; `/_/github.json` follows the frozen choice and the current grant.
- **Cleanup execution.** Due cleanups for the configured app run immediately (`waitUntil` after withdraw, Retry and failed callbacks) and every cron tick in `apps/jobs`. Uncertain ones still wait for reconciliation (11D).
- **No cache purge added.** `/_/github.json` stays `no-store` with `CDN-Cache-Control: no-store` (Phase 40), so no shared cache entry exists; withdrawal is immediate through D1. Adopting the planned five-minute `s-maxage` after S-9 must add an explicit purge. `apps/jobs/src/publication-cache.ts` is untouched (another worktree is editing it).
- **Folded fix.** The `fix/github-cleanup-redirect` change (`redirect: "manual"` for revocation, 3xx is retry) is included here with its tests, per the owner's choice. That branch and its uncommitted record can be discarded.
- **UI.** Figma `200:2025` (read-only, session `f8bf7eed-…`) shows an "Include private activity / Optional" switch, a one-line privacy note, an outlined "Authorize private activity" button and a hint. The panel follows it, with the product's required visitor-visibility explanation, Authorize again / Use public activity only for failures, and a confirmed Remove private access. Nothing in the file was changed.

Cursor Bugbot follow-up on PR 52 (`5237696`), both findings confirmed and fixed:

- **A delivered token could escape revocation.** After the exchange returned a token, an ended session, a moved portfolio or a storage or fetch failure threw before anything was queued. The attempt then stayed `exchanging` until the crashed-callback deadline released the reservation, while the token stayed valid at GitHub. Now any such failure queues the token for token-only revocation and finishes the attempt. `discardIssuedToken` no longer needs a live session; it acts only on the reserved grant of the consumed attempt's operation. A portfolio mismatch in `finishConsent` no longer uses the "already queued" error. A callback that throws also starts the cleanup sweep. New persistence step: a session ending during the exchange leaves a pending token-only grant that cleanup deletes. A mutation check (restoring the old rethrow) fails it with `Expected "pending", received "consent"`.
- **A bad activity key was silent and broke the public graph.** An invalid `GITHUB_ACTIVITY_KEY` was treated as "unset" by the sweep and turned public status, preview, setup, detect and retry into 503. Graph routes now continue without private activity, consent still fails closed, and the sweep logs the misconfiguration and rethrows. Revocation can't run without the key, since queued tokens are encrypted with it, so rows stay queued until it is repaired. New route test (1).
- Checks after the fix: `pnpm check` (630 tests) and `pnpm test:persistence` (97 checks). The full gate was not rerun.
